# CI Baseline — Inspection and Canonical Gates

Milestone: `LOCAL QUALITY GATES → CI → VERIFIED GREEN CI`.
Scope is CI only: no features, no architecture, no contract, schema, or
security-behavior changes.

## Phase 1 — Inspection of the existing CI

### 1. Which CI workflows already exist

One: `.github/workflows/ci-cd.yml` (workflow name `CI`).
Triggers: push and pull_request on `main` and `develop`.
Concurrency group cancels superseded runs on the same ref.

Jobs on HEAD (`3c5795c`):

- `api` — Python 3.12, `postgres:16-alpine` + `redis:7-alpine` service
  containers, pip install of `requirements.txt` + `requirements-dev.txt`,
  OCR system packages, ruff checks, advisory `mypy`, ad-hoc drift grep,
  `pytest` with coverage flags.
- `migrations-are-reversible` — upgrade/downgrade/upgrade round-trip.
- `web` — Node 20.19.0, `npm ci`, lint, typecheck, test, build.

### 2. Which workflows are incomplete

- No secret-scanner step. `scripts/check_secrets.py --worktree` exists and
  is clean locally but is absent from CI.
- No canonical `alembic check` step; drift is checked with a fragile
  grep over an autogenerated revision instead.
- `TEST_DATABASE_URL` is unset in the `api` job even though the integration
  harness prefers it (`tests/integration/_db.py`, `conftest.py`).
- `requirements-dev.txt` did not pin `greenlet`, which SQLAlchemy's async
  engine needs under `asyncpg` — a clean venv install is the case that
  breaks, i.e. exactly the CI case. (Fixed in this milestone.)
- Coverage is collected with `--cov` but `pyproject.toml` sets
  `fail_under = 80` while the suite currently totals below that, so the
  coverage flags as previously wired would hold CI red for a pre-existing
  gap unrelated to the change under test.

### 3. Which workflows are obsolete

Nothing to delete. The retired NestJS/Prisma references live only in a
code comment; the three jobs all map to the current stack
(React 19 + TS | FastAPI | PostgreSQL 16 | Redis 7 + RQ).

### 4. Which commands are currently executed

Backend: `ruff check` + `ruff format --check`, `mypy app` (advisory),
`alembic upgrade head`, autogenerate drift grep,
`pytest --cov=app --cov-report=term-missing --cov-report=xml`.
Migrations job: upgrade / downgrade / upgrade round-trip.
Frontend: `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`
(`vitest run`), `npm run build` (`tsc -b && vite build`).

### 5. Which commands are missing

- `python scripts/check_secrets.py --worktree` (security gate).
- `alembic check` (canonical drift gate; replaces the autogenerate grep).
- `TEST_DATABASE_URL` export for the backend test run.

### 6. Which secrets are required

None. CI runs on throwaway values only: `caprep:caprep` on the ephemeral
PostgreSQL service, local Redis, and non-secret Vite build placeholders
(a real-shaped Supabase URL plus `sb_publishable_ci_placeholder`).

### 7. Which services are required

PostgreSQL 16 (service container, `caprep_test`) — required by the
migration steps and the integration suite. Redis 7 — kept because the
`api` job already declares it and the health surface assumes a reachable
Redis; the unit suite itself mostly uses `fakeredis`/mocks.

### 8. Whether CI can run without production credentials

Yes. No test path reads a production Supabase, database, AI key, Razorpay
secret, or JWT secret. The suite passes on the disposable values above.

### 9. Whether tests require PostgreSQL

Yes. `tests/integration/` and `tests/test_integration_db.py` execute real
SQL. Without a database they skip by design; with one they run — which is
why the migration step must precede pytest in CI, on a fresh database.
The harness truncates every table between tests but keeps
`alembic_version`, so the schema is migrated in, never created by hand.

### 10. Whether tests require Redis

Not strictly: queue-boundary tests run over `fakeredis` and contract tests
mock the client. The service container stays because it is cheap and
covers any route-level Redis touch.

### 11. Whether frontend tests require external APIs

No. All 248 Vitest tests run offline against mocked fetch/Supabase.

## Local-environment findings (recorded so they are not re-diagnosed)

1. This shell exports `DEBUG=release`, which breaks `Settings` parsing
   (`debug` must be a bool). CI runners do not set `DEBUG`; local shells
   must simply not export it.
2. Local databases `caprep_test` / `caprep` are stamped with revisions
   (`0014_*`, `0015_*`) that do not exist in this repo — residue from a
   sibling checkout. A fresh database migrates cleanly to head
   (`6c3f7b0a0c13`); CI is unaffected (always a fresh service container).
3. `pytest.ini` takes precedence over `pyproject.toml [tool.pytest.ini_options]`
   when pytest runs from `apps/api`, so the canonical flags are
   `-q --strict-markers` from `pytest.ini`. CI runs plain `pytest`.

## Phase 2 — Canonical CI gates

Security: `python scripts/check_secrets.py --worktree` (strict; negative
controls verified: planted live-shaped Supabase secret and planted remote
DSN with password each exit 1).

Backend (`apps/api`, `ENVIRONMENT=test`, disposable PostgreSQL + Redis):
`pip install -r requirements.txt -r requirements-dev.txt`, then
`alembic check`, `pytest -q -rs` (plain: `pytest.ini` strict-markers stay
on). No `--cov`: `fail_under = 80` predates this milestone and must not
gate merges.

Migrations: `alembic upgrade head`, `alembic downgrade base`,
`alembic upgrade head` on a fresh database.

Frontend (`apps/web`, Node 20.19.0): `npm ci`, `npm run typecheck`,
`npm run lint`, `npm test`, `npm run build` with placeholder Vite env.
